# v0.1.7 vs v0.1.8 Worker benchmark on the A40 (2026-10-02)

Machine: NVIDIA A40-24Q (vGPU VM), 60 vCPU; another user's JVM build used
about 8 cores throughout, the same for every run. Binaries: release builds of
`v0.1.7` (`5cc7d56`) and `v0.1.8` (`6cd271a`), both with the 256x256 NVENC
probe (v0.1.7 needs the local benchmark patch, v0.1.8 ships it). Workload:
`bench_per_commit_fixture_1080p_120f.mkv` (FFV1 1080p, 120 frames, untagged),
warmed TensorRT cache, `anime-2x` SR, RIFE 2x FI (239 4K frames). Runs
alternate v0.1.7/v0.1.8. Harness and logs: ignored
`.omo/benchmarks/v017-v018-20261002/` (`matrix.sh`, `decode.sh`, `matrix.txt`,
`decode.txt`).

## End to end, FFmpeg 8.1 (wall seconds, 3 runs)

| Workflow | v0.1.7 | v0.1.8 | Change |
|---|---:|---:|---:|
| SR -> FI, hevc_nvenc | 14.83 / 15.71 / 15.69 (15.41) | 15.15 / 15.81 / 14.48 (15.15) | -2%, within noise |
| SR only, hevc_nvenc | 9.91 / 9.63 / 9.69 (9.74) | 9.42 / 9.39 / 9.39 (9.40) | -3.5% |
| SR -> FI, libx265 | 20.13 / 19.46 / 20.50 (20.03) | 20.40 / 20.04 / 20.87 (20.44) | +2%, within noise |

- The first v0.1.7 SR->FI NVENC run took 7:59 with FI at 8 s per pair while the
  TensorRT sessions loaded from cache in 0.2 s; GPU memory was 1.3 GB higher
  than in any other run, so another GPU process was active. It was discarded
  and replaced by a fourth pair. One extra v0.1.8 run (14.62 s) agrees.
- Per-frame stages are unchanged: SR inference 37-42 ms, FI 115-180 ms per
  pair, NVENC encode 24-33 ms, x265 encode 47-52 ms.
- Conclusion: no measurable throughput change between the versions with
  FFmpeg 8.1. The SR-only gain is small but consistent (SR inference 39.3 ->
  37.5 ms); its cause was not isolated.

## accurate_rnd+full_chroma_int decode cost (decode only, 120 frames)

`decode.sh`: the VideoInput command line, `scale=in_color_matrix=bt709`, rgb24
to a pipe, `flags=bicubic` (v0.1.7) vs `bicubic+accurate_rnd+full_chroma_int`
(v0.1.8).

| FFmpeg | bicubic | +accurate_rnd+full_chroma_int |
|---|---|---|
| 8.1.2 (bundle) | 1.15 s wall, 7.0 s CPU | 1.20 s wall, 10.0 s CPU |
| 4.4.2 (Ubuntu 22.04) | 1.28 s wall, 7.4 s CPU | 2.83 s wall, 9.6 s CPU |

- With 8.1 the decoder still runs at about 100 fps, far above the 4K pipeline
  (10-25 fps), so the extra 40% CPU does not reach wall time.
- With 4.4 (single-threaded swscale) it adds about 13 ms per frame, which is
  still below the pipeline's per-frame time; it matters only on CPU-starved
  hosts.

## Docker image FFmpeg (v0.1.7 image: Ubuntu 22.04 FFmpeg 4.4.2; v0.1.8: bundle 8.1)

Simulated on the host with the same v0.1.8 binary and the system 4.4.2
package that the v0.1.7 image installs (same Ubuntu 22.04 package). The
images themselves were not run.

| Workflow (v0.1.8) | FFmpeg 4.4 | FFmpeg 8.1 | Speed-up |
|---|---:|---:|---:|
| SR -> FI, hevc_nvenc | 22.89 / 22.43 / 22.22 (22.51) | 15.15 | 1.49x |
| SR only, hevc_nvenc | 13.10 / 13.08 / 12.77 (12.98) | 9.40 | 1.38x |

NVENC encode is 58-62 ms/frame with 4.4 (single-threaded rgb24 -> yuv
swscale) vs 24-31 ms with 8.1. The Docker change is the only large
performance difference in v0.1.8, and only for Docker users.
