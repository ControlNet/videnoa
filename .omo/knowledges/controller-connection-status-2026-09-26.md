# Controller sidebar connection status

- The sidebar footer reflects the browser-to-Controller SSE connection, not Worker health or scheduler execution. Sources: `controller-web/src/events/SessionEvents.tsx` and `controller-web/src/shell/AppShell.tsx`.
- The authenticated shell opens native `EventSource("/api/events", { withCredentials: true })`. Healthy and initially connecting states render no status text. An error maps to `unavailable` when readyState is CLOSED, otherwise `reconnecting`. Current labels are `Controller unavailable` and `Controller reconnecting`; the current Controller frontend has no literal `disconnected` label.
- Opening the stream or receiving a valid update restores connected state. Before the sleep-recovery fix below, native EventSource owned all reconnection and CLOSED had no application-managed restart.
- Errors invalidate page data with reason `reconnect`. Each server connection starts with `refetch`; the frontend invalidates data again to fetch current state. Task, Worker, and scheduler changes arrive as typed delta events.
- `crates/controller/src/operations/events.rs` uses a 64-entry broadcast channel; lag produces `refetch` rather than historical replay. It enables Axum default keepalive (15-second maximum interval in installed Axum source), checks authentication passively on a 30-second interval, and ends the stream on failed authentication or shutdown. Passive checks do not renew session idle expiry.
- A degraded stream can leave displayed progress stale while backend work continues. The status alone cannot diagnose transport interruption, server restart, proxy behavior, or session expiry. Inspect the browser Network entry for `/api/events` and correlated Controller logs to distinguish them. A healthy pending HTTP 200 event-stream request is expected.
- Initial investigation did not change application behavior. Existing lifecycle regression coverage is in `controller-web/src/auth/AuthApp.test.tsx`, test `reports the actual event-stream lifecycle`.

## Recovery after computer sleep

- The user reports frequent `unavailable` after computer sleep and returning to the browser window. The missing CLOSED recovery path explains why a terminated connection could stay unavailable; the original transport failure has not been captured from the user's browser.
- `SessionEvents` now recreates CLOSED streams with exponential retry delays of 1, 2, 4, 8, 16, then at most 30 seconds. Opening a connection resets the delay. Extra retries run only while the page is visible and the browser reports online.
- Visibility, focus, online, and pageshow events immediately recover CLOSED or failed CONNECTING streams. Healthy OPEN streams and fresh connection attempts remain untouched, preventing overlapping recovery signals from repeatedly replacing a new attempt. Native EventSource still handles ordinary CONNECTING retries.
- Replacing a stream aborts its event listeners and closes it. Unmount clears timers, stream listeners, and browser lifecycle listeners. Reconnection retains the existing server `refetch` snapshot-refresh mechanism.
- `controller-web/src/events/SessionEvents.test.tsx` uses an explicit test-only EventSource substitute to cover bounded backoff, reset after open, lifecycle recovery, snapshot invalidation, stale callbacks, native reconnect ownership, hidden/offline deferral, and unmount cleanup. These tests do not reproduce physical OS sleep or prove the deployment's transport failure cause.
- Verification: `npm --prefix controller-web test`, `npm --prefix controller-web run lint`, and `npm --prefix controller-web run build`. Expect passing tests, no lint errors, and a successful production build. Manual deployment check: sleep and wake the client, return to the Controller window, and verify `/api/events` reconnects and task progress refreshes without reloading the page.
