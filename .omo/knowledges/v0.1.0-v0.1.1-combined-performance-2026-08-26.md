# v0.1.0 vs v0.1.1 combined FI and SR performance

Date: 2026-08-26

## Conclusion

On an NVIDIA A30-24C, exact-tag `v0.1.1` improved the cache-hot `FI -> SR` workflow over exact-tag `v0.1.0` while producing decoded-frame-identical output.

- End-to-end median throughput: `4.0034 -> 4.6305` output FPS, a `15.665%` uplift.
- End-to-end median wall time for 47 output frames: `11.740 -> 10.150` seconds, a `13.543%` reduction.
- CLI warmed processing median: `5.6 -> 8.3` input-equivalent FPS, a `48.214%` uplift.
- Median peak RSS: `5932.0 -> 5831.1` MiB, approximately `1.7%` lower.
- Median paired end-to-end uplift: `16.063%`; pair range: `5.057%` to `17.753%`.
- All ten measured outputs and both warmup outputs had decoded framemd5 stream SHA-256 `0446f75f41f06bb376abda217dcca4d0f27c1f3abdc22dad38391ecfc0064a78`.

Use `15.7%` as the measured short-clip end-to-end improvement. Use `48.2%` only when referring specifically to the CLI's warmed processing metric, which excludes its first two input-equivalent frames and does not represent complete invocation latency.

## Cache behavior

The first successful runs were warmups and were excluded from the measured table. At these tags, `VIDENOA_DATA_DIR` correctly changes the runtime config location but does not redirect the TensorRT compile cache used by these workflow nodes. With the repository as the working directory, the observed cache paths were:

- v0.1.0: shared root `trt_cache`, eight cache files before warmup.
- v0.1.1 RIFE: namespaced `trt_cache/device-0_af25762dfec02a4bbb949decea63988b01fa56c46c0ff9dc66ac8e2f12cbb661_1088x1920`, initially empty and populated during warmup.
- v0.1.1 SR: namespaced `trt_cache/device-0_7666ddb0b9078e9fd47bf961e718a67715ad28894477be588d1fe69a9418a0a5_1080x1920`.

The measured samples therefore represent each release's normal cache-hot behavior after a successful full warmup. Cold engine-build time is deliberately not compared.

## Reproduction outline

Build each exact tag in a detached worktree with a separate Cargo target directory, then run the same absolute workflow and input paths from the repository root. The runtime environment is:

```bash
export ORT_DYLIB_PATH="$PWD/lib/libonnxruntime.so"
export TRT_LIBS="$HOME/miniconda3/envs/anime/lib/python3.13/site-packages/tensorrt_libs"
export LD_LIBRARY_PATH="$TRT_LIBS:$PWD/lib:$HOME/miniconda3/envs/anime/lib:$LD_LIBRARY_PATH"
export PKG_CONFIG_PATH="$HOME/miniconda3/envs/anime/lib/pkgconfig:$PKG_CONFIG_PATH"
export RUST_LOG='videnoa_core::pipeline=info,videnoa_core::nodes::backend=info,videnoa_app=info'
```

The command surface supported by both tags is:

```bash
VIDENOA_DATA_DIR=/tmp/version-specific-data \
  /path/to/exact-tag/videnoa run \
  "$PWD/presets/interpolation-2x-anime-2x.json" \
  --input "$PWD/.omo/benchmarks/combined-performance-2026-08-25/input-24f.mkv" \
  --output /tmp/measured-output.mkv
```

Do not pass `--backend`, `--data-dir`, or `--log-filter` to the `v0.1.0` `run` subcommand. The preset selects TensorRT; use `VIDENOA_DATA_DIR` and `RUST_LOG` for boundaries supported by both tags.

Validate decoded output independently of container metadata:

```bash
ffmpeg -v error -i /tmp/measured-output.mkv -map 0:v:0 -f framemd5 - \
  | sha256sum
```

## Interpretation limits

- The 24-frame fixture keeps repeated GPU runs practical but makes startup, TensorRT session loading, decoding, and encoding a large fraction of wall time.
- End-to-end output FPS is the conservative user-facing number for this exact short clip.
- The CLI FPS is useful for the pipeline's warmed processing rate but should not be presented as complete invocation throughput.
- This benchmark establishes a clear improvement on the tested A30, workflow, models, resolutions, and cache-hot state. It does not establish performance on other GPUs, backends, model combinations, or cold cache builds.
